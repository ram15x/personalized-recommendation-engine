# DCN rating ranker: implementation and next evaluation protocol

## What exists now

`scripts/dcn_ranker.py` implements a DCN-v1 style regression model. It concatenates user and item embeddings with numeric features, sends this shared representation through a vector cross network and an MLP, then predicts one explicit MovieLens rating. `test_dcn_ranker.py` checks output shape, finite gradients, rejection of an out-of-vocabulary ID, and Keras save/load.

One bounded MovieLens diagnostic was trained from a 500,000-row sample of the fixed 70% training window and evaluated on 2,000 sampled users from the 70/80 period. The final, clipped-comparison metrics and saved artifacts are in `reports/development/dcn-rating-diagnostic-70-80-2026-11-05-clipped/`; the narrative report is `reports/development/dcn-rating-diagnostic-70-80-2026-11-05-corrected.md`. It performed worse than a simple user/item-mean baseline on rating RMSE/MAE and on ranking among those users' actually rated validation items. The panel is reused development data, and that observed-item ranking diagnostic is not an ItemKNN-candidate evaluation. The diagnostic DCN is not promoted or evidence of improved recommendations. A different saved candidate-conditioned pointwise ranker is exposed by an opt-in native API route. Two earlier run reports are marked superseded because of comparator implementation errors; do not cite them.

## Why this target and architecture

MovieLens 25M contains explicit star ratings, not impressions or click events. The TFRS basic ranking tutorial predicts ratings for user/movie pairs with mean squared error; that is a suitable task match for this dataset, but it does not turn ratings into CTR ([TFRS ranking tutorial](https://www.tensorflow.org/recommenders/examples/basic_ranking)). The DCN paper introduces cross layers for learning bounded-degree feature interactions ([Wang et al., 2017](https://arxiv.org/abs/1708.05123)). That motivates testing crosses among user, item, and context features; it does **not** establish that DCN will beat ItemKNN or popularity on this project.

The model emits an unbounded regression score trained against ratings; clip to 0.5–5.0 before displaying or comparing it as a rating. Do not call it click probability, CTR, or an online ranking score. A later supervised ranking dataset may use only observed ratings as labels; unrated items must not silently become negative examples.

## Resource-bounded serving candidate

The Docker demo now serves the saved sparse ItemKNN candidate for liked/highly-rated histories, with explicit-genre and popularity fallbacks. This is a classical item-item collaborative-filtering method, not a novel architecture; the original item-based formulation is described by [Sarwar et al., WWW 2001](https://www.ra.ethz.ch/CDstore/www10/papers/519/). This implementation binarizes observed ratings at `>= 4`, computes cosine-normalized co-rating neighbors, keeps the top 100 neighbors per item, and scores a user by summing neighbor weights from supplied positive history. The checked artifact has 13,173 indexed items, 1,309,591 nonzero similarities, and a 5.13 MB matrix file. Its sparse scoring requires no GPU. The 60/70 evaluation found better matched NDCG@10 and Recall@100 than popularity but no significant matched Recall@10 difference; the window was already used in development, so this supports a demo path only, not an independent performance claim. The native API exposes the experimental two-tower and candidate DCN through opt-in routes; the Docker browser demo does not enable them.

## Candidate-ranking evaluation and results

1. **Data and order:** use the already-local `data/ml-25m/ratings.csv`; verify its SHA-256 against the recorded value before reading. Keep equal timestamps together. The earlier 70/80 panel has already been used in DCN and other Project 2 development; do not call it fresh validation. Never use the official final 10% for training, tuning, or model choice.
2. **Candidate source and results:** hash-manifested exports exist for the corrected 50/60 and 60/70 sampled windows. Both ItemKNN scripts sample up to 2,000 training-positive users with any held-out observation (seed 42), without using rating values to select users, and compute similarities in 64-row blocks. Two DCN scorers were trained on observed candidate labels from 50/60 and evaluated on the 386 user IDs shared with 60/70. The pointwise MSE model had lower NDCG@10 than ItemKNN order, with a paired interval crossing zero. The pairwise objective had a larger negative NDCG@10 difference, with its paired interval below zero. Neither model is promoted; the pointwise candidate model has an opt-in native API route. See `reports/development/dcn-itemknn-candidate-ranker-50-60-to-60-70-v1.md` and `reports/development/dcn-pairwise-candidates-50-60-to-60-70-v1.md`. The prior 86-user pilot is low-support and not evidence. Earlier saved retrieval metrics used a future-positive-conditioned cohort and remain historical. Unrated candidate outcomes remain unknown and are not training negatives. These reused windows are development evidence, not an independent test.
3. **Time-safe ranker examples:** use candidate sets generated only from history available at each simulated recommendation time. Train on observed labels from a preceding time window, then evaluate later candidates, with candidate-generation and ranker-training periods separated. Existing 50/60, 60/70, and 70/80 panels have already been used during development; all further results on them remain development evidence, not independent test results.
4. **Features:** user ID and item ID embeddings plus values computed only from the corresponding retrieval/ranker training history (user rating count/mean, item rating count/mean, genres known at recommendation time, and the ItemKNN retrieval score). Fit numeric normalization statistics on ranker-training examples only. Map unseen IDs to reserved row zero and report their support separately.
5. **Labels:** predict the observed 0.5–5.0 rating with MSE as the training objective. For ranking metrics, define rating >=4 as a positive preference proxy; observed lower ratings are non-positive rating labels. Unrated candidate items have unknown outcomes and are not training negatives. State that observed-rating evaluation is affected by MovieLens exposure/selection bias.
6. **Baselines and metrics:** compare the DCN and a simple training-period mean-rating scorer on the exact same retrieved candidate lists and users. Report rating RMSE/MAE; candidate Recall@100/500 and coverage before ranking; then NDCG@10 and Recall@10 after ranking, both overall and by warm/cold support. Report candidate-set positive support and the maximum achievable recall from the retrieved candidates. Do not report CTR.
7. **Decision:** retain a ranker only if its paired per-user NDCG@10 difference versus unchanged retrieval order is positive with a 95% paired user-bootstrap interval excluding zero, candidate recall is unchanged by design, and warm/cold support and rating errors are reported. Neither tested candidate-conditioned DCN passes this gate. This is a development gate, not proof of production value.

## Scope still required by the assignment

This document records an evaluation contract and the candidate-ranker checks completed so far. Still missing are a ranker that passes the comparison gate, verified end-to-end learned retrieval and ranking, Triton model inference, an Airflow retraining-task execution, a real online A/B test, and measured CTR. The optional ItemKNN artifact route has passed a live HTTP check. The Docker Compose popularity/content demo and Redis integration were checked on 5 November 2026. A Spark feature-table job exists, but the current staging-folder cleanup change and a MovieLens 25M execution have not been verified in a Spark runtime. Online metrics require click/impression data and real traffic; MovieLens alone cannot provide them.

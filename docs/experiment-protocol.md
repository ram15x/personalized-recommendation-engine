# Project 2 experiment protocol

This protocol is the gate before another recommendation model is trained. It is based on the portal brief and the files and results already in this folder. It does not claim the current retriever is useful.

## What the current evidence says

- The existing 25M baseline uses a global timestamp split: first 80% train, next 10% validation, final 10% test. The final 10% already has a popularity-baseline result recorded; do not use it to choose architectures or settings (`reports/ml-25m/metrics.json`).
- The saved two-tower pilot used 500,000 of 9,981,093 available training-positive rows, only 3 epochs, and indexed 12,224 of 34,461 items. Its saved comparison on 2,000 selected users is below popularity, and the cohort was reused (`reports/retrieval-pilot/metrics.json`, `reports/candidate-recall-diagnostic-2026-11-04-v2/metrics.json`).
- On warm users in that reused cohort, the saved-vector diagnostic gave Recall@500 0.155 for retrieval and 0.298 for popularity. The output is a candidate-stage diagnostic; its NumPy scoring did not load the FAISS binary.
- The fixed genre-profile baseline also lost to popularity on the same warm-user cohort. It is a rejected simple baseline, not evidence that all item metadata features fail.
- A saved Colab run used all 9,981,093 positive training pairs (3 epochs, T4-visible, about 278 seconds), but still lost badly to popularity for warm users: Recall@10/NDCG@10 **0.000262 / 0.001484** versus **0.01902 / 0.07259**. On the same indexed catalog, candidate Recall@100 was **0.00446** versus **0.13285**. Its loss stayed near **5.104** across the three epochs. This is from the old reused validation period, not a new test; see `reports/existing-colab-retrieval-audit.md`.
- The initial Nov 5 scoring pass used a positive-only item catalog (18,405 items) as the denominator and reported 100% coverage; that result is invalid and preserved only for traceability. A corrected three-epoch run used the full 22,931-item rated training catalog. It indexed 18,405 items (80.26%). On 3,550 users with learned embeddings, Recall@100 was 0.00438 over all eligible targets and 0.00494 on indexed targets, versus popularity 0.14821 on that same indexed-target subset; top-10 Recall@10 was 0.00045 vs 0.03362. The other 15,853 users had no learned embedding (15,843 had no prior history; 10 had prior history) and used popularity. Loss was nearly flat. See `reports/development/two_tower_70_80_fullcatalog_2026-11-05.md`; this is a development diagnostic, not an independent test.

## Split and comparison rules

1. Use only the already-local MovieLens 25M file. Do not copy or download the raw data.
2. Preserve global time order and keep equal timestamps on the same side of a boundary.
3. For the next development cycle, split the old first-80% period into an earlier 70% training window and its following 10% validation window. The audit script reports actual rows and support because timestamp ties may shift exact percentages.
4. Train every candidate and its popularity baseline using only that earlier training window. Do not evaluate historical checkpoints here: they trained through the old 80% cutoff and therefore saw this proposed validation period.
5. Do not use the old 80-90% window for model selection; earlier retrieval development reused it. Keep the old final 10% away from experiments. Its baseline score is already known, so any eventual one-time score there must be labeled as a previously reported holdout comparison, not a pristine untouched benchmark.
6. Freeze feature construction, candidate catalog, target definition, seed, and metric code before the first new training run. No metric or cohort redesign after looking at candidate results.
7. Report candidate Recall@100/200/500, user coverage, catalog coverage, warm/cold supports, and NDCG@10/Recall@10 after ranking. Show popularity on the identical users and candidate availability. Report CTR only if actual click logs or a real online experiment exist.

The corrected 70/80 run had 19,403 validation users with positive targets. Of these, 3,560 had any earlier history, but only 3,550 had positive-training embeddings; 10 had history but no embedding, while 15,843 had no history. For the 3,550 embedded users, 110,095 of 124,777 target pairs (88.23%) were represented in the index, yet retrieval Recall@100 on that indexed subset was 0.00494. The overall index representability rate was 95.16% of target pairs; do not confuse this with successful retrieval. The earlier 4 November audit used different counts and is reported separately. Historical retrieval checkpoints trained through the proposed 70/80 validation window and are not valid candidates for its comparison.

## Model sequence and decision gate

1. Re-establish popularity using the fixed 70/80 training window and same validation users; the corrected script already reports it in this diagnostic.
2. Do **not** repeat the full-data fit just to increase epochs or change architecture names. The 9.98-million-pair run and corrected 8.75-million-pair run both failed to beat popularity. Inspect the custom in-batch loss and training signal: verify positive-pair/user/item ID mapping, gradients and embedding norms, batch-mask behavior, score distributions, and retrieval/exclusion implementation. Compare the custom loss with the TFRS `Retrieval` task and `FactorizedTopK` metric on the frozen development split; TFRS documents these as retrieval objective and top-K evaluation tools ([TFRS API](https://www.tensorflow.org/recommenders/api_docs/python/tfrs/tasks/Retrieval), [FactorizedTopK](https://www.tensorflow.org/recommenders/api_docs/python/tfrs/metrics/FactorizedTopK)).
3. Only after a short, inspectable sanity run shows finite gradients and a meaningful training signal, train one new candidate on the 70/80 protocol. Save its exact split manifest, parameters, seed, code revision, training history, and candidate item IDs.
4. Evaluate retrieval quality before adding a ranker. If it does not beat popularity on the warm-user cohort or fails user/item coverage checks, diagnose sampling, ID coverage, training objective, and candidate generation before building downstream complexity.
5. The proposed retrieval architecture is a TFRS two-tower with learned IDs plus available item metadata (genres); warm users use their learned/history signal. A new user with no history can only be personalized if the demo collects a preference signal, such as favorite genres or liked seed movies. With no history or preference input, use popularity and label it non-personalized. This design is a hypothesis, not implemented or validated.
6. For unseen items, use metadata features only when the item would have been available at the simulated recommendation time. Keep the popularity baseline restricted to the same available catalog. Do not let future movie availability leak through the candidate set.
7. Only after candidate coverage is adequate, generate ranker-training candidates with a second time-safe split inside the training period. Exclude candidate-generation labels from the retriever's fitting data for those ranker examples. Compare popularity ordering with one DCN or Wide & Deep ranker on identical candidates.
8. A small DCN ranker is the first candidate because it explicitly models feature crosses, but it is not automatically better. Its original research targets click prediction; here `rating >= 4` is only a preference proxy and unobserved items are uncertain negatives ([DCN paper](https://arxiv.org/abs/1708.05123)). Report the proxy label and negative-sampling rule; never call the result CTR.
9. Build Spark, Redis, Triton, and Airflow integrations in separate, small steps after offline data and model interfaces are stable. A MovieLens offline split cannot establish an online A/B win or CTR.

## Research basis

TensorFlow Recommenders describes retrieval as selecting hundreds of candidates from a large catalog, then ranking those candidates into a shorter list. Its tutorial treats retrieval candidate recall as a stage-specific metric and exports the query model plus candidate index for serving: [TFRS retrieval tutorial](https://www.tensorflow.org/recommenders/examples/basic_retrieval) and [TFRS ranking tutorial](https://www.tensorflow.org/recommenders/examples/basic_ranking).

Global timeline alignment matters: recommender evaluation work documents that ignoring a global timeline can expose future interactions and change model rankings. A recent RecSys paper also reports that split strategy can materially affect offline conclusions: [Ji et al., *A Critical Study on Data Leakage in Recommender System Offline Evaluation*](https://arxiv.org/abs/2010.11060), [Gusak et al., *Time to Split*](https://doi.org/10.1145/3705328.3748164).

The current FAISS `IndexFlatIP` is exact inner-product search, not approximate search. It is a sensible correctness baseline; only consider approximate indexing after the saved vectors, item coverage, and exact retrieval behavior are sound: [FAISS index guide](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes), [FAISS index selection guide](https://github.com/facebookresearch/faiss/wiki/guidelines-to-choose-index).

## Latest fixed item-neighbor comparison

The frozen binary-positive, cosine item-neighbor method (top 100 neighbors per item) scored above popularity on matched-catalog Recall@100, Recall@10 and NDCG@10 in both the 50/60 window and the fixed 60/70 replication. Matched Recall@100 differences were +0.07433 (95% interval +0.07006 to +0.07901, 4,274 warm users) and +0.07689 (+0.07209 to +0.08152, 4,820 warm users). Exact run metrics, support and caveats are in `reports/development/itemknn-50-60-results-2026-11-05.md` and `reports/development/itemknn-60-70-replication-results-2026-11-05.md`.

Interpret this only as a development signal. The method was selected after earlier model outcomes and 60/70 followed the 50/60 ItemKNN result. Neither panel is an independent final test, and rating >= 4 is not click data. The candidate is not integrated into the API, and no online CTR or A/B conclusion follows. Keep the current popularity API in place until a serving artifact and separate untouched evaluation are designed and verified.

## Current state

At the time of the original split audit, no model was trained and no data was downloaded. Two three-epoch 70/80 Colab runs have since been recorded: the first evaluation had a positive-only catalog bug; the corrected run used the full training catalog denominator and still scored below popularity. A BPR comparison on that same 70/80 window also remained slightly below popularity. A fixed BPR recipe was then run on the earlier 60/70 window using the existing ratings file and Colab T4. It also remained below the matched popularity baseline (Recall@100 0.15805 vs 0.16334; paired 95% CI -0.00683 to -0.00367). It was not promoted. Although the 60/70 window was frozen before scoring, the BPR objective was chosen after inspecting 70/80 results; this is not independent model selection. The later fixed ItemKNN candidate exceeded popularity on matched-catalog Recall@100, Recall@10 and NDCG@10 in 50/60 and a 60/70 temporal replication, but it was selected during development and is not independent evidence. The ItemKNN candidate is not integrated into the API. See the ItemKNN result reports for exact metrics and limitations. The host has a 4 GiB RTX 3050, but TensorFlow 2.15 reports no visible GPU; its native Windows GPU support ended after TensorFlow 2.10 (official install guide: https://www.tensorflow.org/install/pip). WSL queries returned Wsl/E_ACCESSDENIED. TFRS/FAISS remain absent locally; they were installed in the scratch Colab runtime.

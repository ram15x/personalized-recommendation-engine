# FAISS candidate-aligned ranker development protocol

Recorded before export and model fitting. The 10,000-user support pilot found only 756 early observed candidate ratings and 57 users with candidate ratings in both halves. Expand to all 108,155 users represented in the existing `reports/retrieval-pilot` artifact, without a data download. This choice followed the pilot; neither this window nor the resulting metrics is independent.

Use the existing two-tower embeddings and exact FAISS index frozen before the 80% timestamp, `1466837400`. Use first-half observed ratings in `[1466837400,1490935654)` for ranker development and the second half `[1490935654,1515033908)` for development evaluation. Users are eligible for each half if they have any rating in that half, selected without using rating values. Exclude all movies rated before each half from that user's FAISS candidates. For each user retrieve up to 100 items from the unchanged index and record their raw FAISS scores. Store labels only for candidate items with an observed rating in the corresponding half; unlabeled candidates are not negative training examples. Store all unseen observed positive movies in the period for Recall@10; absent or unretrieved positives count as misses. This is an exposure-biased offline evaluation, not CTR.

To avoid unsupported user/item embeddings, the prospective ranker is a small DCN-style model operating only on the FAISS score and a popularity-rank feature from the frozen retriever artifact. It has no trainable user/item IDs and should be usable for every retrieved candidate. Fit feature normalization on observed first-half candidate labels only. Predict explicit rating with MSE; use the fixed threshold rating >=4 for positive relevance metrics. Use an unmodified FAISS order and training-period popularity order on the exact same retrieved candidates and user cohort as comparisons. Report per-user Recall@10 and NDCG@10, support, users without positive targets, and 2,000 paired bootstrap intervals by user. Exclude users with no unseen positive outcomes from relevance-metric means, but report them. Candidate-stage recall and catalog coverage must be separate from ranking metrics. All choices and models remain development-only. No result will be described as independently validated or as a click-through result; no model is promoted without the pre-existing paired evaluation gate and a working end-to-end check. Never use outcomes at or after `1515033908` for fitting or selection.

Expected storage is limited to compressed per-user candidate lists, numeric scores and observed labels; do not copy the 25M CSV or download anything. Stop and report if source hashes, candidate mapping, or temporal checks fail. The final-period ratings are not retained or used; computing the input checksum reads the complete file bytes.

Implementation fixed before this first model fit: two continuous inputs (raw FAISS score and zero-based popularity rank divided by catalog size); two vector cross layers and a 16/8-unit ReLU deep branch; an unbounded rating output trained by MSE, Adam 0.001, batch size 256, four epochs, seed 42, CPU. No validation-driven epoch choice, hyperparameter search, or training on unlabeled candidate items. Normalization is fit only on first-half observed candidate-label rows. Record all epoch losses and both end-to-end and candidate-conditioned results. Keep this candidate experimental regardless of the result until the existing evaluation gate and end-to-end integration are assessed.

## Targeted initialization check, recorded after v1 and before v2

A post-run check on the 8,313 training labels found v1 final training MSE 50.2815 versus 0.9767 for the training-label mean. Its prediction quantiles included -38.47 and 177.30. Among 8,313 rows, 26 had a standardized input magnitude above 6 and contributed 8.19% of total squared error; large inputs alone do not explain the whole error. Hypothesis: initializing the final output as the observed training mean rather than a random projection gives a sane starting prediction and lowers training error. This hypothesis is motivated by v1 and is not a preregistered independent comparison.

Fixed v2 change: use a zero output kernel and bias equal to the training-label mean. Keep the feature data, four epochs, batch size, model layers, learning rate, time windows, candidate lists, and evaluation code fixed. No feature clipping and no additional tuning. Compare the v2 training MSE and same-candidate metrics with v1 and the same FAISS and popularity baselines. The development window is reused and results cannot establish generalization; the pre-existing promotion gate still applies.
